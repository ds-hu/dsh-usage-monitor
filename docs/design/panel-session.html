面板会话：把草稿与写入锁从 React 里搬出来

候选 2 的核心伪代码。评审这份数据流、不变量与失败模式；定了我再改代码。

1. 现在的摩擦（可量）

  • usePanelController 一个函数：289 行、12 个 useState、6 个 useRef、6 个 effect，返回 25 个成员，其中 savedBanner 是 JSX、advancedRef 是 DOM 引用。
  • 7 个异步守卫手工对账：editorId、opSeq、mountedRef、testSeq、revision、togglingRef、settingsWrites。
  • 「保存进行中」有两个家：控制器里的 toggling，与模块级的 settingsWrites——视图在渲染时直接读后者来决定禁用态（orderedRows）。
  • 后果：这类「迟到回调不得污染新草稿」的规则只能靠渲染整个面板来验证；test/browser/edit-identity.spec.mjs 有 13 个用例专门守它，全部要起浏览器。

2. 方案 A（推荐）：一个面板会话模块

把草稿生命周期、写入身份与「回调是否还算当前」收进一个模块；React 只剩订阅与视图态。它是一个模块级的单例，不是每次渲染新建——因为写入必须在面板关掉后继续成立。

接口（调用方只需要知道这些）

createPanelSession({ post, reload, surface }) →
{
  subscribe(fn) / getSnapshot()        // 一个不可变快照，视图只读它
  begin(supplierId | null)             // 打开编辑：给 id 进供应商草稿，给 null 进全局设置
  setField(key, value)                 // 改当前草稿的一个字段（同时推进 revision）
  test(supplierId)                     // 连接测试：草稿优先，否则用已保存配置
  save()                               // 保存当前草稿（编辑器或全局）
  discard()                            // 明确放弃当前草稿
  toggle(supplierId)                   // 启停
  leave()                              // 回到目录（脏草稿先请求确认，见下）
}

快照

{
  editor: { supplierId, editorId, origin, form, initial, revision } | null,
  globalForm, dirty, globalDirty,
  opBusy,                      // 当前草稿有写在飞（禁用整张表单）
  lockedIds: string[],         // 有写在飞的供应商（视图据此禁用，不再读 settingsWrites）
  togglingIds: string[],
  test: { supplierId, revision, result } | null,
  saved: "global" | supplierId | null,
  failure: { message, fields: ("threshold" | "secret" | "transport")[] } | null
}

写一次的全部路径

save():
  op = identity()                    // { editorId, seq: ++opSeq }
  if (opBusy || pendingWriteFor(current)) return        // 合并重复点击
  publish({ opBusy: true, saved: null, failure: null })
  outcome = await post("/settings", patchOf(current))   // 网络，可能很慢
  await reload()                                        // 取服务端真值
  finally { release(current) }                          // 释放锁、唤醒等待者

  // 只有身份仍然匹配时，才允许写任何 UI 字段：
  if (!current(op)) return                              // 静默丢弃，不碰 saved/failure/草稿
  publish({ saved: id, failure: null })
  if (savedSupplier) { surface.showTab(origin); editor = null; editorId++ }

「当前」的判定只在这里写一次：

current({ editorId, seq }) =
  mounted && opSeq === seq && this.editorId === editorId && surface.host is open

不变量（实现必须保证）

#不变量守的是哪个既有用例
1身份不匹配的回调不写任何 UI 字段，也不清草稿保存中切换编辑器：旧回调不清除新草稿
2保存失败保留草稿，只写 failure保存失败保留草稿；重开以服务端为准
3改任意字段使连接测试结果作废（revision 前进），迟到结果按 (supplierId, revision) 丢弃编辑后旧测试返回不显示为当前草稿结果
4锁按供应商粒度：lockedIds 是唯一事实源，视图不得另算启停并发、保存与启停互斥
5草稿只在 discard()、保存成功或面板销毁时清理页签切换与背景重载保留草稿
6面板关闭不取消已在飞的写入；重开时通过 lockedIds 等候关闭在途保存后重开等候服务端状态
7全局与供应商的写互不提前解锁：opBusy 只由自己的 seq 结算全局迟到回调不得解锁供应商保存
8原生设置页与对话框共用同一实例，因此保存锁与草稿身份天然继承原生页接管保留保存锁与草稿身份

失败模式

情形行为
校验不通过（阈值区间）failure.fields = ["threshold"]，视图据此展开「高级」并把焦点移到阈值输入框——不再由控制器持有 DOM 引用
保存请求超时按 transport 处理，草稿保留；不重放（服务端可能已成功）
保存期间供应商被移除begin() 找不到条目即回到目录，failure = null
面板在 post 期间卸载mounted = false，回调丢弃；写入仍在 lockedIds 里，靠快照可见

3. 方案 B：拆成「草稿会话」+「写入队列」

草稿随面板销毁，写入队列独立存在（沿用现在 settingsWrites 的位置）。好处是写入队列将来能被面板以外的入口复用；代价是两者之间要传一个共享的写入身份，不变量 1、7、8 会跨模块表达——规则没有集中，只是变体更小。

我的判断：这一轮的病根是「身份规则散在 7 个 ref 里」，B 把 7 个变成 5 个但要跨两个模块，局部性收益低于 A。除非将来确实有面板之外的写入者，否则不值得。

4. 测试怎么跟着动

  • 新增 store 级用例（无 React）：A 保存中切到 B 的迟到回调、测试结果按 revision 失效、启停并发、关闭后重开的等待——现有 13 个浏览器用例里约 8 个的规则可以下沉到这一层。
  • Playwright 保留：原生设置页接管、焦点回退、Esc 与遮罩、滚动位置——这些是真 DOM 行为，不能下沉。
  • 不采取「先写新的再删旧的」：两套状态同时存在会立刻产生第二个事实源，正是这次要消掉的东西。按行为分组切换，每组切换后跑全量。

5. 回退与边界

  • 不改 wire、不改 CSS、不改可见文案：这是纯前端结构改动，回退就是还原 lib/client.js 一个文件。
  • 不做的事：不引入状态库、不改 surface 状态机（它已经是对的）、不把草稿持久化到 localStorage。
  • 完成判据：settingsWrites 在视图层零引用；usePanelController 不再返回 JSX 或 DOM 引用；单测 + 浏览器用例全绿。
