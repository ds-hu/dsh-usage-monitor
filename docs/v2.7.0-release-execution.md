# v2.7.0 发布执行记录

自 v2.6.0（2026-11-05）以来未发布的三批改动，加上一次年度数据维护。主题是**事实来源各归一处**：限额项的名字、
口径与说明从查询层搬进客户端词典（英文界面不再混中文），明细表不再把人话拼进数据列，说明类文案默认折叠；
同时按 ADR-0001 的年度维护动作补入 2027 年节假日表。

行为变更逐条见 [CHANGELOG](../CHANGELOG.md)，术语定义见 [CONTEXT](../CONTEXT.md)，用户文档见
[README](../README.md) 与 [README.en](../README.en.md)；节假日表的规划与数据复核另见
[2027 年节假日表补录方案](2027-holiday-table-plan.md)。

## 1. 变更摘要

| 面 | 变更 |
| --- | --- |
| 名字与短标签 | 限额项名、窗口短标签与供应商名改由客户端词典渲染，宿主只发「词典键 + 参数」。中文逐字不变，英文界面不再漏中文；供应商列表与供应商页按渲染后的名字排序 |
| 报告口径 | 「周期」列改由 `entry.period`（UTC 今日／昨日）渲染；输入、输出、请求数、到账、赠送、订阅、周加成各自成列，缺项渲染「—」，不补 0 |
| 说明折叠 | 「账单可能延迟」「不覆盖全部产品计量」「月额度无上限」等 8 条说明收进明细里的一处 ⓘ，默认视图只留数据（ADR-0002 的延伸） |
| 周窗口判定 | 不再用 `/周/` 匹配中文名，改用窗口身份（`window.weekly` 这类稳定 key + 供应商声明的窗口长度） |
| 节假日表 | `lib/season.js` 的 `HOLIDAY_VALLEY` 补入 2027 年 29 天；五个调休上班日全部落在周末，仍不单列 |
| 仓库 | 改名 `ds-hu/dsh-token-quota`、脱离 fork network、发布标签改用 `vX.Y.Z`、LICENSE 恢复可识别 |
| 文案 | 净增 49 键（167 → 216）；中英词典同键、同占位符，实测各 216 键 |

### 本轮修掉的一处预检红

`npm run test:browser` 第一趟有 2 项失败：`test/browser/edit-identity.spec.mjs` 的 `openGlobal()` 用
`details.qm-global summary` 定位，而全局设置段里的节假日覆盖表在这次改动中多了一个 ⓘ（内嵌 `<details>`），
同一个选择器命中两个 `<summary>`，Playwright 严格模式直接报错。改成 `:scope > summary`（只取该段自己的
summary）后 34 项全绿。产品侧 markup 不动：ⓘ 在 details 正文里、不在 summary 里，HTML 合法，
`test/browser/interactions.spec.mjs` 当时用的已经是 `details.qm-global > summary`。

### 反向验证

节假日表的「逐项集合比对」断言做过反向验证：把 `"2027-02-13"` 注入成 `"2027-02-14"`（一个调休上班的周日）后
`npm test` 立刻红，失败输出正是 `+ '2027-02-14'` / `- '2027-02-13'`；从备份按字节还原后 sha256 与注入前
逐字节一致（`bfca46ff7634677cdb333f08fb6c9ec03fe6498f23ac28eea8e342a77620bf04`）。

## 3. 存储基准（`scripts/benchmark-storage.mjs`，本机 Windows）

| 供应商 | 历史 | 文件字节 | 保存 p50 | 保存 p95 | 今日统计（24 键 vs 旧式遍历） |
| --- | --- | --- | --- | --- | --- |
| 1 | 7 天 | 15,224 | 11.6 ms | 16.9 ms | 6.2 µs vs 16.8 µs（2.7×） |
| 1 | 90 天 | 194,504 | 20.6 ms | 42.9 ms | 10.1 µs vs 598.2 µs（59.3×） |
| 13 | 7 天 | 196,979 | 25.6 ms | 38.7 ms | 14.5 µs vs 49.4 µs（3.4×） |
| 13 | 90 天 | 2,527,619 | 250.2 ms | 305.1 ms | 17.1 µs vs 768.1 µs（45×） |

与 [validation-report](validation-report.md) 里那组 Linux / Node 22 的数值**不可直接比较**：本机合成负载的字节
体量约为当时的三倍（1 供应商 7 天 15,224 B vs 4,640 B）。介质不是原因：`Get-PhysicalDisk` 显示本机是物理
NVMe SSD（YMTC PC411-1TB-D），而 2.5 MB 的整份同步落盘仍要 250 ms——瓶颈在「每次整份重写再落盘」，不在盘的类型。
结论方向不变：今日统计的读取成本与历史长度基本无关（最多 24 次键查询）。

## 4. 运行时基准（`scripts/benchmark-runtime.mjs`，默认矩阵 12 组）

| 客户端 | 事件速率 | /state p50 | /state p95 | /state p99 | 事件循环 p95 | 用量文件重写 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 0/s | 0.55 ms | 1.21 ms | 2.44 ms | 14.6 ms | 0 |
| 1 | 100/s | 0.75 ms | 2.07 ms | 2.98 ms | 13.4 ms | 0 |
| 5 | 100/s | 0.73 ms | 1.79 ms | 3.96 ms | 14.0 ms | 0 |
| 20 | 100/s | 0.73 ms | 2.35 ms | 3.39 ms | 14.8 ms | 0 |

- 12 组全量：`/state` p50 ≤ 0.80 ms、p95 ≤ 2.57 ms、p99 ≤ 4.04 ms；空闲且配置未变时「用量文件重写」全部为 0。
- 生命周期：5 轮挂载/卸载后活动句柄 2 → 2，RSS 80.4 → 80.3 MB，不随轮次增长。
- 事件循环 p95 落在 13–15 ms，与插件无关：同机、同采样法（自调度 `setTimeout(20)`，预热 1 s、采样 2 s）跑
  **空转** Node 5 轮，基线为 p50 10.6–11.1 ms、p95 12.5–14.4 ms、p99 15.1–16.9 ms，负载值落在基线上方约 1 ms 内。

## 5. 兼容性

- `usage.json` 仍为**版本 2**，桶结构与路径未变；本轮不迁移、不新增存储键。
- 配置无新增字段：2027 表是内置数据，`holidays` 覆盖表的语义不变（非空即整体替换内置表）。
- 从 2.6.0 升级不需要卸载重装：`dsh plugin --profile <p> add @ds-hu/dsh-token-quota` 覆盖安装后**重启 DSH**
  ——`lib/` 与内置表变更不走客户端 HMR。
- 旧版插件读到版本 2 的 `usage.json` 仍按既有单向规则处理：判为不支持并保留原文件。
